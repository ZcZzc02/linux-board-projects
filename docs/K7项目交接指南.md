# K7 LoRa/5G 网关项目交接指南

> 交接对象：继续在 KICKPI K7（RK3576）上维护 LoRa 节点网关、5G/4G/WiFi 上行和 Windows 上位机的开发者。
> 文档定位：这是当前项目的运行与恢复手册，不是规格书。先按“首次接手流程”完成验证，再修改代码。
> Git 基线：`feat/k7-gateway-service-downlink` 分支，提交 `6cd363e`（`fix: avoid modem AT probing in gateway status`）。

## 0. 先读这五条

1. K7 当前能否启动、是否已固定 5G 模块，必须在接手当天重新验证；不要仅凭本文档判断硬件仍正常。
2. LoRa 使用的是 K7 的 `/dev/ttyS3`，不是官方镜像默认占用的 I2C7。UART3 依赖专门的 boot/resource 产物，重刷官方全量镜像后会丢失该配置。
3. 业务网关代码已在 Git 中；节点板工程、旧 STM32 网关工程和 Windows 上位机目录目前**没有完整纳入 Git**。交接时必须把它们作为源码快照单独打包。
4. 当前实际 MQTT Broker 是 `broker.emqx.io:1883`，topic 前缀是 `fengyan_daq_2026`。K7 与上位机前缀不同就无法互通。
5. RG200U-CN 未用 Mini-PCIe 固定螺丝时出现过 USB 反复掉线。软件可重连，不能修复接触不良；固定模块后再做稳定性验证。

### K7 网关的现有能力

- 接收 `/dev/ttyS3` 的 E22 LoRa 数据，验证 CRC-16/MODBUS 后解析。
- 解析 `0x01` AD7606、`0x02` CAN、`0x03` RS485 和 `0x41` RS485 透传帧。
- 将数据写入 `/var/log/k7-gateway/lora.jsonl`；可选原始日志为 `/var/log/k7-gateway/lora.raw.log`。
- 向 MQTT 发布数据和网关状态，并订阅下行主题。
- 支持 `rs485_raw`、`rs485_read`、`rs485_write`、`relay + bus=can` 和 `relay + bus=rs485` 下发命令。
- 使用系统默认路由决定当前上行类型；蜂窝优先，WiFi 仅为兜底。

### 不能误解为“已经完全验收”的部分

- F767 的 CAN 上行通过真实 PCAN 工具做过端到端验证。
- LoRa 节点上行、AD7606 上报、MQTT 上报和后台显示已验证过。
- RS485 协议/下发帧已经实现，但最近阶段没有重新做完整真实从机闭环验收。
- 5G 模块在手动强力按压时做过 60 秒连续测试，未发生枚举/断连；未固定螺丝前仍不能算长期稳定。

### 4.3 刷写历史与安全边界

已执行过的恢复思路是：先用 FactoryTool v1.89 刷入官方 Ubuntu 全量镜像，恢复可正常显示的屏幕和 WiFi；随后恢复带 UART3 的 boot/resource 方案，使 LoRa 可以走 `/dev/ttyS3`。

**全量刷机和只写 boot 是不同操作。**全量镜像会覆盖 eMMC 内的数据；只写 boot 仍可能让设备无法启动或造成黑屏。接手者在任何写入前必须：

1. 用 ADB/串口记录当前版本、分区表和服务状态。
2. 备份当前 boot 分区和系统信息，且把备份复制到电脑外部。
3. 校验待写文件 SHA-256。
4. 明确当前工具界面选中的是官方全量镜像，还是 boot 分区镜像；不能把 boot 文件当成 FactoryTool 的全量 `update.img` 使用。

不要根据猜测填写 `rkdeveloptool wl` 的扇区偏移。此前的分区写入命令没有作为可复用脚本提交；如果必须再次写 boot，应由熟悉 Rockchip 工具的人先读取当板分区表，在工具界面中明确选中 boot 分区后再执行。错误的偏移会覆写 uboot、recovery 或根文件系统。

`work/boot-uart3.its` 和 `work/sdk-dts-backup-20260627/` 保存了当时重新打包/修改设备树的线索。它们不是一键重编内核流程；要重新构建应在 Linux/WSL 的 K7 SDK 环境中进行。

## 5. 硬件状态、接线与物理风险

### K7 与 E22 LoRa

- LoRa 模块：E22-400T22D。
- K7 使用 UART3，对应 Linux `/dev/ttyS3`。
- 逻辑电平必须是 3.3 V TTL；不要接 5 V TTL。
- 模块读取配置时，M0/M1 需要进入配置模式；透明传输工作时，当前接法是 M0=GND、M1=GND。
- 已读取到的 E22 配置响应：`C100090000006500170B0000`。
- 旧网关兼容参数：433 MHz、信道 `0x17`、9600 8N1、19.2 K 空中速率、22 dBm、透明传输。

更完整接线和 E22 模式说明见 [`../2.1.Linux网关/k7-gateway/docs/LoRa_E22接线与UART选择.md`](../2.1.Linux网关/k7-gateway/docs/LoRa_E22接线与UART选择.md)。

### STM32F767 节点板

- 节点工程：`2.节点F767/Onenet_BigBoard (2)_V4/Onenet_BigBoard/USER/工程文件.uvprojx`。
- 已编译且应随交接包保留的固件：`USER/Objects/工程文件.hex`。
- 节点负责 AD7606、CAN、RS485 与 LoRa 打包/转发。
- 本阶段没有为 K7 迁移而修改节点板源代码。若将来改 LoRa 帧格式、频率、地址或功能码，才需要使用 Keil 修改/重刷节点。

### Quectel RG200U-CN

- 模块接在 K7 的 Mini-PCIe 4G/5G 插槽，SIM 卡插在 K7 板载的 SIM 卡座，不插在 RG200U 模块本体。
- 外接天线必须按模块丝印接 ANT0/ANT1/ANT2/ANT3；不要在模块上电时反复插拔天线。
- Mini-PCIe 卡必须用与板载支柱匹配的短 M2 固定螺丝锁住。螺丝长度以不顶到主板为准，通常是 M2 x 3 mm 或 M2 x 4 mm，先和支柱实际高度确认。
- 最近一次在手动强力按压模块时，连续 60 秒观测到接口稳定、无 `USB disconnect`、无 RG200U 重新枚举、MQTT TCP 连通约 185–294 ms。此前不固定时出现过 `ttyUSB0`–`ttyUSB4` 消失和 `enx*` 网卡重建。

结论：当前最大风险是物理固定，而不是网络守护代码。安装螺丝后应连续运行至少 10 分钟，并检查：

```bash
dmesg -Tw
nmcli device status
ip route
systemctl status k7-network-watchdog.service --no-pager
```

如果看到 USB 设备消失，先检查模块是否完全插到底、螺丝、供电和接插件；信号或 APN 问题不会导致 USB 设备从系统中消失。

## 6. K7 上的部署结果与日常操作

K7 上的固定部署目录是 `/root/k7-gateway`。这是板端 Linux 的统一路径，不是 Windows 本机绝对路径；同门应继续使用这个目录以便 systemd 服务无需改动。

### 两个自启动服务

| 服务 | 职责 | 关键行为 |
| --- | --- | --- |
| `k7-gateway.service` | LoRa 收发与 MQTT | 读取 `/dev/ttyS3`，写日志，MQTT 发布/订阅，`--transport auto` |
| `k7-network-watchdog.service` | 链路选择 | 蜂窝优先 metric=100；已保存 WiFi 兜底 metric=600；每 10 秒检查一次 |

服务文件位于：

```text
2.1.Linux网关/k7-gateway/systemd/k7-gateway.service
2.1.Linux网关/k7-gateway/systemd/k7-network-watchdog.service
```

网关服务实际启动参数为：

```text
/usr/bin/python3 -m k7_gateway run-lora
  --device /dev/ttyS3
  --log /var/log/k7-gateway/lora.jsonl
  --raw-log /var/log/k7-gateway/lora.raw.log
  --mqtt-broker broker.emqx.io
  --transport auto
  --mqtt-command-subscribe
  --quiet
```

### 向 K7 更新同一版本的网关代码

在项目根目录运行。`adb` 必须已加入 PATH；若 `adb devices` 没有显示 `device`，先检查 K7 的调试 USB 线、ADB 开关和供电。

```powershell
adb devices
adb shell "mkdir -p /root/k7-gateway"
adb push .\2.1.Linux网关\k7-gateway\src /root/k7-gateway/
adb push .\2.1.Linux网关\k7-gateway\scripts /root/k7-gateway/
adb push .\2.1.Linux网关\k7-gateway\systemd /root/k7-gateway/
adb push .\2.1.Linux网关\k7-gateway\pyproject.toml /root/k7-gateway/
adb shell "cd /root/k7-gateway && sh scripts/install_systemd_service.sh"
```

这组命令会覆盖 K7 的同名应用文件与 systemd 单元，然后重启两个服务；不会擦除 eMMC 分区。更新前需要保留板端日志时，先执行：

```powershell
adb pull /var/log/k7-gateway .\k7-log-export
```

### 日常检查命令

```bash
systemctl status k7-gateway.service --no-pager
systemctl status k7-network-watchdog.service --no-pager
journalctl -u k7-gateway.service -n 100 --no-pager
journalctl -u k7-network-watchdog.service -n 100 --no-pager
nmcli device status
ip route
tail -n 20 /var/log/k7-gateway/lora.jsonl
```

### WiFi 的一次配置与后续自动连接

在 K7 屏幕 GUI 中连接一次热点，或在 K7 shell 执行：

```bash
nmcli dev wifi list
nmcli dev wifi connect "<SSID>" password "<密码>"
nmcli connection modify "<连接名>" connection.autoconnect yes ipv4.route-metric 600 ipv6.route-metric 600
```

密码只保存在 K7 的 NetworkManager 配置中，**不写入 Git、文档或交接压缩包**。蜂窝网络恢复时 watchdog 会将其路由优先级调回高于 WiFi；蜂窝不可用时会继续循环检查并使用可见、已保存的 WiFi。

### 5G/4G 状态的判定

RG200U 的 `quectel-CM` 负责拨号；K7 网关不会在热路径直接抢占 AT 串口。`network_status.py` 优先从 `/tmp/4G.log` 的 `+COPS` 结果识别：

- `10/11/12/13`：上报 `5g`。
- `7/8/9`：上报 `4g`。
- 默认路由为 `wlan*`：上报 `wifi`。

因此后台“GW001 5G 在线”表示默认路由当前经蜂窝网卡并已判断为 5G；不是仅仅检测到模块插着。

SQLite 数据库会在 `server/daq_data.db` 自动生成。为了让不同电脑不互相污染历史测试数据，交接包默认不应包含它；有保留历史数据的需求时另行导出并说明来源。

## 8. 验收顺序：按这个顺序排障

不要一上来同时换镜像、改节点、改代码。每一步通过后再进入下一步。

1. **K7 基础启动**：屏幕可显示、串口可登录，`adb devices` 可见设备。
2. **设备树**：`/dev/ttyS3` 存在；UART3 status 是 `okay`；I2C7 status 是 `disabled`。
3. **E22**：配置模式执行 `python3 -m k7_gateway e22-read-config --device /dev/ttyS3`，得到已知配置响应。
4. **LoRa 上行**：节点板上电，K7 `listen-lora` 能看到有效 `RX_HEX` 与 JSON。
5. **网络**：`nmcli device status` 和 `ip route` 显示实际默认出口；MQTT 可连 `broker.emqx.io:1883`。
6. **上位机**：页面连接 EMQX/WebSocket，出现网关状态和节点数据。
7. **下发**：先用只读 `rs485_read`，再测试 CAN/RS485 下发，避免一开始执行写寄存器或控制负载的命令。
8. **稳定性**：固定 5G 模块后，持续运行 10 分钟以上，检查无 USB 重枚举、无 MQTT 频繁断线。

K7 上常用单次验证：

```bash
cd /root/k7-gateway
PYTHONPATH=src python3 -m k7_gateway self-check
PYTHONPATH=src python3 -m k7_gateway network-watchdog --once
PYTHONPATH=src python3 -m k7_gateway listen-lora --device /dev/ttyS3 --seconds 30 --raw
```

开发电脑上的回归测试：

```powershell
cd .\2.1.Linux网关\k7-gateway
$env:PYTHONPATH = "src"
python -m unittest discover -s tests
```

最后一次代码回归的结果为 29 个单元测试通过。测试只覆盖 Python 协议、MQTT 编解码、网络选择逻辑；它不能代替真实 LoRa、SIM、CAN 或 RS485 硬件测试。

- `.venv`、`__pycache__`、日志文件、SDK build 输出、压缩包副本。
- WiFi 密码、SIM 卡信息、MQTT 账号/密码、token、私钥或 API key。

## 10. 交接后的第一件 Git 事

当前仓库已跟踪 K7 网关和 Windows 上位机，但两块 STM32 工程仍是未跟踪目录。建议接手者完成一次硬件复验后，按以下边界建立可回溯历史：

1. `k7-gateway` 继续保留在当前仓库并从 `feat/k7-gateway-service-downlink` 开发。
2. 上位机目前已在本仓库跟踪；如需独立发布可再拆为 `daq-host-server` 仓库，并忽略 `.venv`、`daq_data.db`、`__pycache__`。
3. F767 节点板单独建立 `f767-node-firmware` 仓库，忽略 `USER/Objects`，只在 Release 附件保留经过验证的 `.hex`。
4. 旧 G070 网关作为 `legacy-stm32-gateway` 只读参考仓库，不与 K7 业务代码混改。
5. 每个仓库的 README 写清硬件版本、烧录工具、版本号、实际验证命令和已知限制。

这样后续“改 K7 网络逻辑”“改后台 UI”“改节点协议”可以分别提交、回滚和审查，不会再混在一个不可追溯的文件夹里。

## 11. 当前已知问题与下一步优先级

| 优先级 | 事项 | 原因与验收标准 |
| --- | --- | --- |
| P0 | 固定 RG200U-CN | 安装合适的 M2 螺丝；连续运行 10 分钟无 USB disconnect/re-enumeration |
| P0 | 对新电脑完成第 8 章验收 | 确认交接包和真实板卡都完整 |
| P1 | 将上位机/F767/旧网关导入各自 Git 仓库 | 消除关键源码未跟踪的风险 |
| P1 | 重新做 RS485 真实从机闭环 | 验证读、写、透传和超时日志符合预期 |
| P1 | 做 5G/4G/WiFi 切换长测 | 观察默认路由、后台 transport 标识、MQTT 不中断或可恢复 |
| P2 | 用 K7 SDK 正式重建设备树/boot | 将当前 boot/resource 候选从二进制备份提升为可重复构建的产物 |

接手过程遇到问题时，先导出 `journalctl`、`dmesg`、`nmcli device status`、`ip route`、`adb devices` 和上位机终端日志，再决定是硬件、系统、网络还是应用层问题。不要在没有日志的情况下直接重刷镜像。
