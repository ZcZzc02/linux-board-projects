# K7 新板从零复现与完整交接

本说明适用于旧 K7 丢失后，在另一台 Windows 电脑、另一块新购买 K7 上恢复网关功能。先读本文，再读 `docs/INTERFACE_SPEC.md`。旧版“同门接手说明”假定旧板仍在，不能代替本文。

资料整理日期：2026-10-16。包内 `BUILD_INFO.json` 记录实际源码提交、构建环境与收录范围；`MANIFEST.json` 记录每个文件的字节数、SHA-256 和来源。

## 1. 能恢复什么，资料是否齐全

恢复目标：

```text
CAN / RS485 / AD7606 -> STM32F767 节点 -> E22 LoRa
    -> K7 UART3 -> CRC / 帧解析 -> MQTT -> HiveMQ -> Windows 上位机
后台命令 -> HiveMQ -> K7 -> E22 LoRa -> 节点 -> CAN / RS485 设备
K7 的互联网出口：RG200U 蜂窝网络优先，已保存 WiFi 兜底
```

本地已找到并收录：官方 Ubuntu 全量镜像、历史修好的 UART3/resource 版 boot、配套 resource、官方 boot 回退、官方 Loader/parameter、K7 网关和后台完整源码、节点源码与 HEX、旧 STM32 网关协议参考、测试、系统服务、烧录工具/驱动、ADB、板卡原理图、离线厂家文档及图片。

这套资料支持按既有方案在匹配的新 K7 上恢复与继续开发，但有以下实际边界：

1. **没有已部署好全部业务、含旧板根文件系统的最终全量克隆镜像。**实际恢复方式为“官方全量系统 + 修正版 boot + 应用部署”，这三部分都在包内。
2. 旧板已经丢失，无法再从旧板导出文件、核验最后一次运行配置，也无法现场测试新板。包内二进制检查和单元测试不等于新板硬件验收。
3. 新板 PCB 版本、内存规格、触屏型号可能与旧板不同；采购时向厂家确认是否兼容这份 2025-12-09 K7 Ubuntu 镜像，不要擅自换成 K7C/K7S 或 Android。
4. 完整 Rockchip SDK、交叉工具链与源码构建环境未收录；这不影响既有镜像烧录、Python 网关部署。包内有相关 DTS/脚本和最终 DTB，若要重新编译整个内核，需另行获取匹配版本的完整 SDK。
5. Windows 需安装 Python 3.11（以及继续用 Git 时的 Git）；后台 Python 依赖安装需要互联网。包内没有 Python 安装器、Keil 授权或完整离线 pip 仓库。
6. WiFi 密码、SIM PIN、APN 认证、SSH 私钥不从旧电脑迁移；新用户自行配置。旧 STM32 网关源码快照中的 WiFi/密码宏在打包时脱敏，详见 `BUILD_INFO.json`。

## 4. 首先验证文件，识别哪份镜像能干什么

Windows 安装 Python 3.11 后，在解压根目录的终端执行：

```powershell
py -3.11 .\scripts\handover\verify_package.py
```

输出 `PASS` 才代表解压文件与清单一致。这会读取大镜像，请耐心等待。单个 ZIP 超过普通附件限制时使用网盘或大文件传输；不要把 `.img` 文件打开再另存为。

| 文件 | 类型/作用 | 如何使用 |
| --- | --- | --- |
| `firmware/official/update-rk3576-...191847.img` | 4,204,509,827 字节，官方完整更新包，含 rootfs、内核、Loader 等 | 第一步 FactoryTool 或 RKDevTool 的完整固件升级 |
| `firmware/uart3/boot-resource-uart3.img` | 67,108,864 字节，历史成功方案的 **boot 分区镜像** | 官方系统启动正常后，第二步只恢复 boot；不能作为完整更新包 |
| `firmware/uart3/resource-uart3.img` | 936,960 字节，已经包含在上面的 boot 中 | 保留追溯，不额外寻找“resource 分区”写入 |
| `firmware/baseline/boot-official-baseline.img` | 旧板导出的 64 MiB 官方 boot | 回退参考，需核对新板布局 |
| `firmware/loader/parameter.txt` | 原完整更新包拆出的分区说明 | 对照新板分区；不是可以随意复制地址的烧录脚本 |

### 修正版为什么能同时兼容屏幕与 LoRa

此次解析 FIT 和 Rockchip RSCE resource 后确认：修正版保留官方内核、FIT 层原始 FDT、两张启动 logo，并在 resource 的六份 K7 屏幕设备树中仅改两处 `status`：

```text
/serial@2ad60000 : disabled -> okay
/i2c@2aca0000   : okay -> disabled
```

六份包括默认/HDMI、5 英寸、8 英寸、两种 10.1 英寸适配。FIT 层 FDT 仍为官方默认状态属于这个历史方案的特征；不能只查看 FIT 那一份 FDT 就断言没开 UART3，也不能用它替换所有屏幕的设备树。

检查报告：`firmware/inspection/boot-inspection.json`。最终生效仍要以新板重启后的 `/proc/device-tree` 和显示结果验收。

早期 `boot-uart3-inplace-v2.img`、不匹配的单 FDT 打包、黑屏的旧同门镜像都不作为推荐烧录文件收录。`references/device-tree/boot-uart3.its` 只留作历史线索，它不是本次验证成功镜像的保证可复现构建配方。

## 5. Windows 开发环境和软件点击顺序

1. 安装 Python 3.11 x64、Git、VS Code（Codex 可继续使用）。包内无需 Keil 才能运行 Linux 网关；只有改 STM32 节点代码才需 Keil。
2. 管理员运行 `tools/DriverAssistant-v5.13/DriverInstall.exe`，点击驱动安装。只在驱动冲突时按厂家步骤卸载旧版再安装。
3. 先将新板断电，按新板丝印找到用于调试/烧录的 Type-C，使用数据线接电脑。
4. 需要串口时安装 CH340 驱动。包内未找到独立 CH340 安装器，可通过 Windows 更新或芯片厂商获取；Rockusb 驱动与 CH340 驱动不是同一种。
5. 用包内 ADB，不要求新电脑有原电脑的盘符：

```powershell
.\tools\platform-tools\adb.exe devices -l
```

`device` 是正常运行系统的 ADB 状态；`Loader/Maskrom` 是烧录状态。两种状态同时用于不同软件，不能互相替代。

串口软件可用 `tools/serial-terminal/` 中的 MobaXterm 程序，操作路径 `Session -> Serial -> 选择 COMx -> Speed 输入 1500000 -> Advanced: 8/N/1、None flow control -> OK`。若下拉没有该速率，直接输入。一个 COM 口同一时间只让一个软件占用。

## 6. 第一步：新板刷入官方 Ubuntu，先确认显示

此步会覆盖新板 eMMC，任何出厂数据需要先备份；操作前确认只有目标 K7 接在烧录工具上。本文为交接操作说明，本次打包没有连接或写入任何硬件。

1. 打开 `tools/FactoryTool-v1.89/FactoryTool.exe`。
2. 点击 `Firmware`，选择 `firmware/official/update-rk3576-kickpi-k7-linux-ubuntu-multi-20251209-191847.img`。等待文件选择和载入完成，核对芯片 RK3576。
3. 选择 `Upgrade`。新板是未知系统时，需先核实厂商推荐的升级模式；不要随意选择擦除/Restore。
4. 按住板上 `RECOVERY` 再上电，工具识别 `Loader` 后松手。无法进 Loader 时，依据新板的官方说明使用 `MASKROM`，不要短接未知焊点。
5. 点击 `Run` 后等待；写入期间不拔电/USB。看到 `Upgrade OK`、绿色成功并且失败数为 0 后，点击 `Stop` 再关闭工具。
6. 按工具/板卡说明退出烧录模式正常启动，首次启动留足初始化时间，屏幕正常后再操作。
7. 官方系统中先验证屏幕、触摸、WiFi、ADB。此时 `/dev/ttyS3` 可能不存在，是已知官方默认配置，不是要重写网关源码的证据。

如路径包含中文导致老烧录工具无法加载，可将整个解压目录放到短的纯英文路径；项目代码仍不依赖该具体路径。

厂家带截图的步骤见 `references/vendor-docs/pages/common/zh/rockchip/usb-shao-lu.md`，相对图片放在同包 `assets/`。多屏自适应镜像不能任意替换分区镜像，下面只针对本包严格匹配的修正版 boot；其他内核/屏幕版本不应照搬。

## 7. 第二步：恢复 UART3 的 resource 版 boot

此步仅写 boot，不刷 rootfs。写错 boot 仍可能无法启动，需要回到上一步救援。不要把 64 MiB boot 文件放到 FactoryTool 的 `Firmware`。不要使用猜测的 `mmcblk2p3`、扇区地址或其他板卡的 boot。

### 7.1 只读检查与上传文件

在解压根目录执行；如果多个 ADB 设备同时在线，在每条 adb 命令中加 `-s <实际序列号>`。

```powershell
$adb = '.\tools\platform-tools\adb.exe'
& $adb devices -l
& $adb shell "id; uname -a; cat /proc/device-tree/model"
& $adb shell "ls -l /dev/disk/by-partlabel/boot /dev/block/by-name/boot; lsblk -o NAME,SIZE,PARTLABEL"
& $adb push .\firmware\uart3\boot-resource-uart3.img /tmp/boot-resource-uart3.img
& $adb push .\scripts\handover\restore_uart3_boot.sh /tmp/restore_uart3_boot.sh
& $adb shell "sh /tmp/restore_uart3_boot.sh"
```

默认脚本只检查：root、精确 K7 model、名为 boot 的真实块设备、64 MiB 分区、待刷镜像 SHA、当前是否是已知官方 boot。若与本包基线不同会拒绝继续；**不要删检查或强行指定分区**。记录错误、当前分区与型号，让 Codex 和厂家先核实新板兼容性。

如果 ADB 不是 root，确认该官方 Linux 镜像如何获得 root；不要猜账户密码。可通过串口登录有 sudo 权限的账户再用 `sudo sh`，但必须保持前述检查。

### 7.2 人工确认后执行

确认目标是新 K7 的 boot、镜像校验一致、官方启动显示正常后执行：

```powershell
& $adb shell "sh /tmp/restore_uart3_boot.sh --apply-I-CONFIRM-BOOT-OVERWRITE"
```

脚本通过命名分区定位，不包含固定扇区地址；先在板上 `/root/k7-recovery-backups/<时间>/boot-before.img` 备份并校验，才执行 `dd` 写 boot，写完做全分区回读 SHA。它不会自动重启。

输出 `WRITE_VERIFIED` 后先把原 boot 导出：

```powershell
& $adb shell "cat /tmp/k7-boot-backup-location.txt"
# 上一条输出的目录就是下一条的源路径；替换占位符。
& $adb pull /root/k7-recovery-backups/<实际目录>/boot-before.img .\new-board-boot-before.img
& $adb reboot
```

这是本次新增的受保护复现入口，已做语法/静态检查，因旧板丢失尚未在新硬件执行。若 ADB 不可用，可用 RKDevTool 3.30 的分区界面，但必须先读出新板分区、确认命名与大小，由接手人确认仅 boot 写入；不要照抄历史截图里的地址。

### 7.3 重启后验收

```powershell
& $adb wait-for-device
& $adb shell "ls -l /dev/ttyS3"
& $adb shell "cat /proc/device-tree/serial@2ad60000/status; echo; cat /proc/device-tree/i2c@2aca0000/status; echo"
```

期望：屏幕和触摸仍正常，串口设备存在，UART3=`okay`，I2C7=`disabled`。有任何一项不符先停在此步，导出串口启动日志；不要同时接入 LoRa、改后台、改节点来掩盖问题。

## 8. 第三步：接 E22 LoRa 与节点

设备树 pinctrl 原文：UART3m0 RX=`GPIO3_A1`，TX=`GPIO3_A0`。包内 `references/vendor-docs/assets/K7_PIN-*.png`、IO 电压图和 K7 原理图用于查新板实际排针编号。不要把 GPIO 编号当作物理针脚号。

| 信号 | 连接原则 |
| --- | --- |
| K7 TX | 经适当电平转换后接 E22 RXD |
| K7 RX | 经适当电平转换后接 E22 TXD |
| GND | K7 与 E22 共地 |
| VCC | 按 E22 厂家额定供电并满足发射电流，不把供电电压等同于 UART 逻辑电平 |
| M0/M1 | 正常透传均接 GND；配置读取时 M0=GND、M1=3.3 V（确认模块手册与电平） |

旧配置响应 `C100090000006500170B0000`；项目约定 9600 8N1、433 MHz、信道 0x17、19.2K 空速、透明传输。新购 LoRa 可能是另一地址/信道，不能因为 UART3 有设备文件就认定无线链路已通。

节点工程和 HEX 已打包；若原节点还在，先不改其固件。更换节点才使用包内 F767 对应工程/固件，并核对实际芯片型号和探针。

## 9. 第四步：部署应用与开机自启

网关是 Python 标准库应用，不用 Keil，也不需要先交叉编译。系统需有 `python3`、NetworkManager/`nmcli`、systemd；这份官方 Ubuntu 预期已带，仍需检查。

电脑运行：

```powershell
py -3.11 .\scripts\handover\deploy_gateway.py
py -3.11 .\scripts\handover\deploy_gateway.py --apply
# 多台 ADB 设备时在两条命令后都加 --serial <实际序列号>
```

第一条只检查；第二条创建标准 tar 包，通过 ADB 部署到 `/root/k7-gateway`，按 LF 换行写入源文件，并安装/启动两项 systemd 服务。该路径是板端服务约定，不是 Windows 盘符依赖。部署会覆盖同名应用并重启服务，已修改过的新板应先备份。

```powershell
& $adb shell "systemctl is-enabled k7-gateway.service k7-network-watchdog.service"
& $adb shell "systemctl is-active k7-gateway.service k7-network-watchdog.service"
& $adb shell "journalctl -u k7-gateway.service -n 50 --no-pager"
```

网关服务接收 `/dev/ttyS3`，保存 JSONL/原始 LoRa 日志、发布 MQTT、订阅下发命令。网络守护负责 NetworkManager 已出现蜂窝网卡和已保存 WiFi 的选择，不负责凭空补全驱动、运营商 APN 或 SIM 激活。

临时手工测试串口前，必须停止正在占用同串口的网关服务：

```powershell
& $adb shell "systemctl stop k7-gateway.service"
& $adb shell "cd /root/k7-gateway && PYTHONPATH=src python3 -m k7_gateway listen-lora --device /dev/ttyS3 --seconds 30 --raw"
& $adb shell "systemctl start k7-gateway.service"
```

节点已上电并发送才期望看到 `RX_HEX` 与 JSON。节点没开时没有新帧不是网关故障。配置读取需要切到 E22 配置模式，完成后恢复 M0/M1=GND。

## 10. 第五步：WiFi 与蜂窝链路

### WiFi 先跑通

在触屏的网络菜单选热点并输入密码，或通过 `adb shell` 进入 K7 后执行：

```bash
nmcli device wifi list
nmcli --ask device wifi connect "<热点名称>"
nmcli connection modify "<连接名称>" connection.autoconnect yes ipv4.route-metric 600 ipv6.route-metric 600
ip route
```

`--ask` 交互输入密码，不把密码写入项目、脚本或提交。

### RG200U-CN

断电安装 SIM 与 Mini-PCIe 模块，按丝印连接匹配天线、用合适短螺丝固定。新卡的 APN、PIN、运营商认证和套餐限制须向供应商核实，不复制他人的值。

```powershell
& $adb shell "ip -br addr; nmcli device status; ip -4 route"
& $adb shell "dmesg | grep -Ei 'RG200U|Quectel|cdc_ncm|disconnect' | tail -n 60"
& $adb shell "command -v quectel-CM; pgrep -af 'quectel-CM|4G_monitor'"
& $adb shell "journalctl -u k7-network-watchdog.service -n 60 --no-pager"
```

旧板曾识别 `2c7c:0900`、`cdc_ncm`、`enx*` 网卡。新板 MAC/网卡名和 IP 不会与旧板固定相同。包内厂家 `4G_monitor.sh` 和 `quectel-CM` 是参考备份，不应在官方已拨号时再启动第二个实例抢 AT 口。

网络优先级是“蜂窝默认路由 metric 100，WiFi metric 600”。4G/5G 制式注册由模块/运营商协商；代码没有实现每次强制锁 5G 再强制锁 4G 的独立拨号状态机。`network_status.py` 参考 `/tmp/4G.log`、ModemManager 或 AT 检测制式；无明确证据时会按 4G 回退，不能因为插了 5G 模块就宣称已驻留 NR。

当路由变化后 MQTT 仍卡住，检查 `journalctl`、TCP 发送队列与实时消息；必要时重启网关服务恢复，不要仅凭 `ss` 的 ESTAB 或页面绿色认定消息已送达。

## 14. 常见问题与恢复

| 现象 | 处理顺序 |
| --- | --- |
| 官方刷完没有 ttyS3 | 完成第二步 resource 版 boot；不是改波特率能解决 |
| 修正版后屏幕卡 logo/黑屏 | 串口抓启动日志，核对包校验、新板型号/屏幕和分区；必要时用完整官方镜像恢复；不要尝试早期候选 |
| boot 脚本拒绝 | 记录 model、boot 名称/大小/哈希，核对是否新版本，不移除保护强刷 |
| ADB 不识别 | 数据线/Type-C 端口/Rockusb 与 ADB 驱动/当前是否 Loader；串口是另一入口 |
| LoRa 无帧 | 节点上电、天线、电平、TX/RX、M0/M1、配置一致、服务是否抢占串口 |
| RG200U 反复消失 | 先查插槽固定、接触、供电、USB 日志，再查模块固件；不能只归咎螺丝 |
| 蜂窝网卡在但不上网 | SIM/APN/注册、DHCP、DNS、路由及到目标 Broker 的真实连接 |
| 页面显示 4G 而预期 5G | 核对模块制式注册及日志更新时间，不能直接改文案强制 5G |
| 后台不更新 | 检查 MQTT/WebSocket、topic/client ID、新消息、默认路由和旧 TCP 发送队列 |
| Python 缺依赖 | 用 `..\.venv\Scripts\python.exe -m pip ...` 安装，不只双击 BAT 猜解释器 |
